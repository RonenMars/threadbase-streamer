## Row 4 — the canary, and why it is the strongest single result here

The owner chose the string `ZZTOPMARKER123` seconds before sending it, typed it by hand on the phone, and sent it as a new session's first message while the capture ran.

**Proof it was received**: the streamer named the session `ZZTOPMARKER123`, `startedAt 2026-09-02T12:20:50.680Z` — inside the capture window (12:20:08–12:21:24Z). The name can only come from the server having read the text.

**Proof it never appeared on the wire**:

| Searched in | Hits |
|---|---|
| decoded WS bytes (28 754 B) | 0 |
| decoded HTTP bodies (26 071 B) | 0 |
| **the raw pcap, unfiltered** | **0** |

Also 0 for `zztopmarker123`, `ZZTOPMARKER`, `TOPMARKER` and `zztop`. Searching the raw pcap matters: it rules out the decode step hiding something, which is the failure mode §14's correction was written about.

## Two coincidental hits, recorded so nobody rediscovers them as a leak

Grepping the first capture for the earlier session's name found `Hi` once on the HTTP leg and `hi` once on the WS leg. Both are chance: the WS one is `-(hic` inside ciphertext, the HTTP one is `...NRHiaG...` inside a base64 Noise blob. A two-character token cannot serve as a canary — which is exactly why row 4 used a 14-character one.

## In the clear by design (not findings)

Request paths and query strings (`GET /api/sessions?limit=50&…`, `POST /api/sessions/start`) per D-7, and the `{"e2ee":{"v":1,"noise":"…"}}` handshake bodies on `POST /api/e2ee/open`.

## Scope

LAN only. The tunnel leg (`tb-secured.rbv1000.win`) is TLS-wrapped and opaque to this method; nothing here is a wire-secrecy claim about it.

## Rig conditions

Scratch `HOME`/config/DB throughout, `--browse-root` pointed at a throwaway `d2-demo` folder. The agent CLI in that scratch `HOME` has **no credentials on purpose** — its login prompt is why the sessions sit at `waiting_input`, and it costs nothing. What is under test is the transport, so an unauthenticated agent's output is evidence exactly like an authenticated one's would be.

## Incidents during the run, both mine and neither a protocol fault

1. **`posix_spawnp failed` on every session start.** The rig's `node-pty/prebuilds/darwin-arm64/spawn-helper` was `-rw-r--r--`: the rig's `npm install` ran with postinstall scripts blocked, so the exec bit was never set. Fixed with `chmod +x` on the scratch copy. Worth a streamer issue — the message names nothing an operator could act on.
2. **An unanswerable prompt makes a session completely uninteractive from the phone.** The unauthenticated agent's login selector never resolves, and the client's "A prompt is waiting for an answer" guard blocks sending in the **Terminal** view as well as chat, so neither a message nor a raw keystroke can be sent. Independent of E2EE; worth a mobile issue. Worked around by putting the canary in a *new* session's first message, which travels in `POST /api/sessions/start` before any prompt exists.

I also sent one ESC to the PTY server-side (`{"ok":true}`) while diagnosing (2); it did not clear the selector.
