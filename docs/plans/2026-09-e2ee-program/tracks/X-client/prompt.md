## Scope — two PRs, sequential

**XC1 — context, ticket, WebSocket.**
- `services/e2ee/record.ts`: seal/unseal over `@stablelib/chacha20poly1305` with the AAD from `NONCE-DESIGN.md`; the counter is a `bigint` (or a representation that throws, never wraps, at 2^53 — decide and justify in the plan; interop against W1a's fixtures byte-for-byte).
- `services/e2ee/context.ts`: contexts opened against the stored static keys via `POST /api/e2ee/open`, keyed by **server id**. **Owner ruling 2026-08-29 (NONCE-DESIGN.md §8): one context per channel instance** — each WebSocket connection opens its own context and gets its ticket from that open (the context dies with the socket; a reconnect is a new open, never a reused socket context), and REST has one long-lived context per server (24 h / 1 GiB / foreground **rollover** past the threshold — never an in-place rekey (NONCE-DESIGN §6): the client opens a *new* context and retires the old one; the server drains the old context for 10 s, then answers `E2EE_CTX_UNKNOWN`; kept on background). One transparent re-handshake on `E2EE_CTX_UNKNOWN`, then a visible error; `E2EE_DEVICE_REVOKED` is a hard failure; pinned server + failed handshake = hard failure, never plaintext.
- `WSClient`: the ticket travels in a request header (`X-TB-Ticket` via `new WebSocket(url, null, { headers })`), never `?ticket=` in the URL (review M12 — URLs land in ingress logs); **a ticketed upgrade carries no `Authorization` header** (W1b ruling: the ticket is the credential — single-use, 30 s, bound to a context proven by the Noise handshake; a bearer beside it is plaintext to the tunnel); delete the `{ type: 'auth' }` frame, **send `{ type: 'register' }` sealed within 10 s of the upgrade** (ruled with the reviewer 2026-08-29: the server closes a sealed socket that has not delivered one valid sealed inbound frame within 10 s of the 101 — the ticket-thief reaper; NONCE-DESIGN §11 contract item), seal in `send`, unseal in `onmessage`, strict `counter == expected`, violation → close and reconnect. Listener registration and the message union untouched.

**XC2 — REST envelope in `authedFetch`.**
- Seal the body, set `X-TB-E2EE: 1`, `X-TB-Ctx`, `X-TB-Seq` (sliding-window semantics on the server; the client just increments), unseal the response before existing JSON parsing. **No `Authorization` header on a sealed request** (NONCE-DESIGN §13(b): the principal comes from the context; a bearer in the clear is the leak the envelope exists to close) — this supersedes mobile-design §4.1's "Authorization carries the device token". React Query, ETags, pagination and error mapping see the same JSON as today.
- Every `api-client` call and every `ws-client` frame sealed on a pinned server — a unit test asserts no plaintext body leaves either module; the **2 s HTTP replay fallback in `useTerminalStream`** is covered by its own spy test ("replay fallback body sealed").

**Review findings bound into this track (`tracks/REVIEW-2026-08-29-mega-brain.md`, read it):** H2 — on a sealed request only a validly sealed response carries application semantics; any unsealed response (401, 304, 426, anything) is a transport failure with backoff, never `AuthError`, never cache freshness, never "re-pair"; no `If-None-Match` on sealed requests; a 426 to a request you sealed is "server/pin mismatch", never a downgrade. M5 — the open is single-flighted per server, the whole `open → ticket → upgrade` sequence is generation-guarded (foreground and the 45 s silence timer both call `forceReconnect`), and the open has its own timeout. **Upgrade failures on a ticketed socket (W1b, §13):** a spent or expired ticket gets `401`, not `426` — there is no credential left to resolve a device from — and RN's WebSocket cannot read the upgrade status or body anyway (M6). Client rule: any failed upgrade on a ticketed socket is treated as `E2EE_CTX_UNKNOWN` — one fresh `/open` (new msg1) and one retry, then a visible error; **never** the re-auth/"pair again" path, which is the H2 social-engineering shape arriving as a status code. Test with a spent ticket and an expired one. M6 — 426 at REST → a specific state ("this server requires encryption for this device") that re-sets the pin when `serverPublicKey` is present; accept that RN cannot see the 426 at upgrade. M9 — run the record and `/open` fixtures **on a device in Hermes** before D2 (`DataView.setBigUint64`/BigInt are unverified there; reuse D-3's throwaway benchmark-screen method). M12 — the ticket travels in a WS header (`new WebSocket(url, null, { headers })`), never the URL. L7/L8 — single-flight the re-open on `E2EE_CTX_UNKNOWN`; retries always re-seal from plaintext, never re-send sealed bytes. **`/open` retries (W1a round 3):** every `/open` attempt — including a retry after a lost response, timeout or 5xx — runs `writeMessage1` afresh with a new ephemeral; the server keeps a replay cache keyed on the cleartext ephemeral and refuses a repeated one as `400 E2EE_HANDSHAKE_FAILED` for up to 24 h, so re-sending the same body is a permanent refusal, not a retry. Test: a lost-response retry produces a different msg1 and succeeds. **PSK length (W1a round 4):** the client's `IKpsk1` path must refuse a PSK that is not exactly 32 bytes (an empty `Uint8Array` is truthy — a truthiness check ran a full IKpsk1 with a constant binding on the server side); the psk-less `IK` path for `/open` must refuse any PSK; both tested. B2 — the response counter must equal the request counter; no `Authorization` on sealed requests.

**Guard-class rules carried from W1a's five adversary rounds (each with its own test):** every byte field (PSK, keys, ctxId, target hash, ephemeral) is checked by one `assertBytes(value, length)` helper — `instanceof Uint8Array`, `BYTES_PER_ELEMENT === 1`, `byteLength === length` — never truthiness or `.length` (a `Float64Array(32)` passed a `.length` check on the server and ran a full handshake binding 256 zero bytes); no `??`/`||` default on any argument reaching a trust boundary (`prologue` is a required parameter; read optional args with `Object.hasOwn`), tested under `Object.prototype` pollution; every piece of nonce/window/context state and every key is an ECMAScript `#private` field (TS `private` is a runtime own property — `(x as any).n = 0n` is the forbidden counter reset); `recordAad` itself enforces that REST channels carry a 32-byte target and the socket channel none; never a getter that returns key bytes — construct the record states from the handshake keys and wipe the source. The 426 handling (M6) fails closed: any unexpected value is "pinned".

**REST wire rules frozen with X-server (reviewer-agreed, 2026-08-29):** (1) no `Authorization` on a sealed request — the principal comes from `X-TB-Ctx`; (2) *a sealed record whose HTTP framing cannot carry a body travels base64url in `X-TB-Env`, in either direction; the body carries it whenever the framing allows one* — so every bodiless request (GET/HEAD/DELETE without body) sends a 46-byte empty sealed record in `X-TB-Env` (target hash in the AAD), never both a body and the header; (3) you MAY send `If-None-Match`; a 304 must carry a valid sealed `X-TB-Env` bound to the request counter or it is a transport failure — an injected `If-None-Match` cannot force an unforgeable 304; (4) the `stop` ndjson reader accepts a single chunk carrying both `stopping` and the terminal event; (5) status map: 409 `E2EE_CTX_UNKNOWN` (plaintext, pre-unseal) → one re-open + retry; 400 `E2EE_SEQUENCE_VIOLATION`/`E2EE_SEAL_FAILED` → protocol error; 413 → bound; 426 → pin mismatch state; any unsealed response other than these plaintext refusals is a transport failure (H2); (6) a status rewrite that induces a retry of a non-idempotent sealed POST (`/input`, `/stop`) double-executes on a new counter — bound retries on those routes (dedup/idempotency on the client), the same hazard plaintext HTTP has.
